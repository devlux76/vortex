# Moon browser smoke test

Moon runs in Chrome. The local Bun process serves the page and pinned model files, runs a real libp2p rendezvous and Circuit Relay v2 server, and hosts a separate Sun test peer. Sun’s local prompts are fixed fixtures. Moon’s three replies are generated by SmolLM2 in the browser. EmbeddingGemma runs in the browser and selects the best match among the namespaces the relay actually returns. Topic descriptions are fixtures supplied by the test page. The test checks that the discovered peer’s signed record verifies, announces Moon, and compares both sides of the conversation under a fresh run ID. Moon reuses one in-memory Ed25519 identity through reconnects.

## Local run

Use Bun 1.4.4 or later and Chrome 157 or later. The one-time fetch stores pinned q4 model files in a directory outside the repo. The browser serves both models from loopback and disables remote downloads. The models and runtime require about 400 MB of disk space.

```sh
bun install --frozen-lockfile
bun v6/tools/moon/fetch-models.ts /tmp/vortex-moon-models
VORTEX_MOON_MODELS=/tmp/vortex-moon-models bun v6/tools/moon/serve.ts
```

Open the printed `MOON_URL` with Chrome DevTools MCP and click **Run smoke test**. Inspect `window.moon`, the Chrome network log, and `GET /sun-transcript` on that URL. A pass has both local ONNX models, 768 finite embedding values, a signed rendezvous announcement, three generated replies, four messages each way, and an exact comparison of Moon’s sent messages against the fixture’s received messages.

## Clouds acceptance run

1. Use the public rendezvous and relay deployment once it has peer admission, per-peer quotas, and a verified CA-signed HTTPS endpoint Clouds can reach. Moon’s browser page and model files can stay local. The browser uses libp2p over secure WebSockets to the relay. Clouds uses the signed HTTPS edge in PR #7. The hub-to-mesh bridge must preserve the room, sender, stable message ID, and reply relation in both directions.
2. Enroll a test room and register the bridge’s peer record under the corresponding rendezvous namespace. Give the test page the relay address, the bridge’s peer ID, and the target and decoy topics in a JSON file. Start the page with `VORTEX_MOON_TARGET=/path/to/target.json` in addition to `VORTEX_MOON_MODELS`. The browser creates a fresh run ID and chooses among the namespaces actually returned by rendezvous. Confirm Moon’s signed record from a separate peer.

   ```json
   {
     "addr": "/dns4/relay.example.org/tcp/443/wss/p2p/<relay-peer-id>",
     "peerId": "<bridge-peer-id>",
     "namespaces": [
       { "name": "moon-webrtc", "topic": "Discover browser peers through a relay and exchange signed messages" },
       { "name": "moon-gardening", "topic": "Grow vegetables in a garden" }
     ]
   }
   ```
3. Have Clouds send fresh prompts over signed HTTPS. Moon posts `MOON <run-id> <turn> <text>` for turns 0 through 3. For each, Clouds replies in the same room with `CLOUDS <run-id> <turn> <text>`. The bridge must present those replies to Moon over the signed mesh protocol from the configured bridge peer ID. Moon generates three browser replies after its hello. Compare both transcripts against the hub and bridge evidence. Require eight alternating messages with the same run ID, four per identity, with matching message IDs, contents, and reply relations. Browser network evidence should show model files coming from loopback and the libp2p connection going to the public relay. Clouds’ evidence should identify the signed HTTPS endpoint and response codes.
4. Drop Moon’s transport after one acknowledged reply, reconnect, renew the relay reservation, and re-register using the same identity. Resume from the last acknowledged cursor and retry one previously acknowledged message ID. Require the conversation to finish with every message visible exactly once.

For initial deployment, run the existing Bun relay and hub on a small host, or keep them on a reachable origin behind a named Cloudflare Tunnel. Preserve the relay key across restarts. Use TTL-based rendezvous leases, renewal before expiry, and bounded retry with jitter after disconnect. Add a second bootstrap address when testing redundancy. The signed message and delivery cursor can survive rediscovery even when a relay circuit is replaced.
